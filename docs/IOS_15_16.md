# Supporting iOS 15 and 16

Undra's Swift output targets iOS 17 by default: a generated store is an `@Observable` class, and Observation is iOS 17 / macOS 14.
An app that still supports iOS 15 or 16 sets its deployment target and gets a second shape of the same store: an
`ObservableObject` with `@Published` properties (ADR-045, SPEC 10.1). Everything under the pixels is the same: the core, the wire, the
C ABI, the XCFramework, Swift 6 language mode and strict concurrency, the commands, the errors, the delivery of changes.

## Turn it on

```toml
# undra.toml
[ios]
deployment_target = "15.0"          # 15.0 or later; the generated stores are ObservableObjects below 17.0
```

`undra bindgen` reads the deployment target: below 17.0 the stores and query handles are `ObservableObject`s, from 17.0 `@Observable`.
`[bindings] swift_observation = "observation" | "observable-object"` (and `undra bindgen --swift-observation MODE`) overrides it;
asking for `observation` with a target below 17.0 is an error that names both settings. A new app starts there with
`undra init todo --ios-deployment-target 15.0`: the Xcode project, the generated Swift package and the three SwiftUI files of the
template are the iOS 15 ones. Switching mode changes the generated files (the second line of each says `// Swift mode: observable-object …`),
so `undra bindgen --check` reports stale bindings until you regenerate.

The Swift runtime itself needs iOS 15 / macOS 12 (`UndraRuntime` and `UndraTestKit` declare it). Below iOS 16 the wire `Duration` is the
runtime's `UndraDuration` (exact nanoseconds, `.zero`, `Hashable`, `timeInterval`) because `Swift.Duration` is iOS 16; from a deployment
target of 16.0 it is `Swift.Duration` again.

## What changes in your views

| | iOS 17+ (`observation`) | iOS 15 / 16 (`observable-object`) |
|---|---|---|
| owning view | `@State private var todos = try! Todos()` | `@StateObject private var todos = try! Todos()` |
| child view | `let todos: Todos` | `@ObservedObject var todos: Todos` |
| environment | `.environment(todos)` / `@Environment(Todos.self)` | `.environmentObject(todos)` / `@EnvironmentObject` |
| outside SwiftUI | `withObservationTracking` | `todos.$visible.sink { … }` (Combine, per property) |
| connection state | `core.connection.state` (`@Observable`) | `@ObservedObject` on `core.connectionObject` |

Reading a signal is still a plain property read, and a command is still a method call; only how SwiftUI is told to re-render differs.
(`@StateObject` evaluates its initializer once, so a store that can throw is created before the view, as the template's `MainApp` does.)
The `$property` publishers are a gain for UIKit and Combine code on every floor. The rest of the iOS 15 SwiftUI surface applies to your
own views: `NavigationView` for `NavigationStack`, no `@Observable` in your own models.

## What degrades

* **Granularity.** With Observation a view re-renders when a property it *read* changes. With `ObservableObject` every view that observes a
  store re-renders when *any* of its published properties changes; the several `objectWillChange` events of one drain are coalesced by
  SwiftUI into one update per run-loop turn. A big store feeding many views is where it shows: split it, or observe a smaller store
  (child stores, ADR-040, help).
* **A big list is copied on every patch.** `@Published` has no in-place accessor, so applying a keyed patch to a list property copies the
  array once (Observation mutates it in place). Measured on an Apple M5 Pro, release build, rows of 32 bytes with a heap string, one patch
  of one op: about 5 µs for 1,000 rows, **48 µs for 10,000** and 0.5 ms for 100,000 under `@Published`, against 0.2 µs at every size under
  Observation. The cost is linear in the list (about 5 ns a row) and is paid once per applied patch, not per op: the mirror merges a
  frame's patches into one apply, so a 100-op patch costs about what a 1-op patch does (56 µs at 10,000 rows), and 100 change-sets in a
  frame publish once (S18; `testAHundredMergedEntriesPublishOncePerSignalOnAnObservableObjectStore`). A phone is slower in absolute terms.
  It is invisible for lists of thousands of rows and worth knowing for lists of 100,000 that change every frame: page them
  ([pagination](../site/docs/cookbook/pagination.html)) or observe a smaller store.
* **One name.** A store member named `objectWillChange` is E0051 in this mode (`ObservableObject` declares it); rename it in the core.
* **SQLite change counts.** The built-in `SQLiteDbAdapter` reads `DbExecuted.changes` with `sqlite3_changes` (a C `int`): `sqlite3_changes64`
  needs SQLite 3.37, iOS 15.4, above the floor. A single statement that changes more than 2,147,483,647 rows reports an undefined count;
  an app's database does not run one, and an adapter of your own is unaffected.
* **Nothing else.** The drain, the keyed patches, `no_coalesce`, the error channel and the mirror are shared code, byte for byte. A drain is
  timed with `DispatchTime` (monotonic, excludes system sleep), `DrainStats.durationNanoseconds` is the field and `duration` an iOS 16 accessor.

## Raising the floor later

Set `deployment_target = "17.0"`, run `undra bindgen`, and make the mechanical edits in the table above (`@StateObject` to `@State`,
`@ObservedObject` to a plain `let`, `.environmentObject` to `.environment`). No core change, no wire change.

## How it is tested

`scripts/ios-floor.sh` runs the proof, and CI runs it (the `ios-floor` job): the runtime builds for the iOS 15.0 simulator and macOS 12; every
golden case of the generator, in this mode, is compiled against the runtime for the iOS 15.0 and 16.0 simulators; `examples/ios15-sample`
(a store with a keyed list, a query handle, deployment target 15.0) builds with `xcodebuild`; the playground's and Fieldbook's bindings
generated for iOS 15 compile for the iOS 15.0 simulator; and the Swift contract grid runs against bindings generated for iOS 15
(`contract-tests/swift/run.sh --floor`). `scripts/ios-floor.sh probe` runs a tiny executable on the booted simulator, built once for an iOS 15.0 and once for an iOS 17.0 deployment target, and checks that `core.connection` is the one `@Observable` connection on an OS that has Observation (a floor build never falls back to the floor path on a newer device). Running the sample on an iOS 15 or 16 simulator runtime happens where one is installed
(`scripts/ios-floor.sh simulator`); the hosted macOS images may carry only a recent iOS runtime, so the build is the guarantee.
