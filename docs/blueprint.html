Design document · working name · prepared for Shrey

Undra

One Rust core under native iOS, Android and web apps. Everything below the pixels, with nothing to apologize for.

Verdict: build it Scope logic + state + data + dev loop UI stays SwiftUI, Compose, React Replaces UniFFI, Crux, and KMP's shared-logic role

§00Verdict: build it, with one scope decision

Go

The gap is real and nobody is closing it. UniFFI generates bindings and stops. Crux gives you an architecture and a thin toolchain. Neither has a web story a frontend team would accept, neither has devtools, neither has a migration path for an existing app. KMP owns Android teams because it is Kotlin, and its iOS and web stories are its weakest parts. There is room for one framework that owns the whole workflow end to end, and the workflow is where the pain is.

The scope decision: Undra owns everything under the pixels. Domain logic, state, data fetching and caching, persistence, offline, auth flows, the dev loop. The UI stays SwiftUI, Jetpack Compose and React. This is the only scope in which "zero compromise" is a true statement rather than a slogan.

The moment a cross-platform framework paints pixels on three platforms it becomes Flutter, and inherits Flutter's compromises: a non-native feel, accessibility drift, and a permanent lag behind each platform's newest UI features. KMP's Compose Multiplatform on iOS is a real product now, and it makes exactly this trade. We refuse it. A SwiftUI view bound to Rust state is indistinguishable from a SwiftUI view bound to Swift state, and that is the bar.

Refusing the pixels still leaves us most of the app. The code below the UI is where the three platforms disagree, where the subtle bugs live, and where every company re-implements the same cache, retry policy, offline queue, pagination and session refresh three times and gets three different answers. That is the code Undra takes over, and taking it over once is what makes teams forget the alternatives.

The thesis in one sentence

Reads never cross the boundary. Writes cross once per transaction. Native UI binds to Rust state as if it were native state. Every architectural decision in this document follows from that sentence, and most of the performance story is that sentence.

What would make me stop

A plan that cannot fail is not a plan. These are the kill criteria, checked at the end of the phase named in the roadmap. If any of them fails and cannot be fixed within two weeks, we stop and write up why.

  • Phase 1: a handle method call with primitive arguments costs more than 500 ns on Android after JNI tuning. The batching design tolerates slow calls, but not that slow.
  • Phase 1: the generated Swift cannot compile warning-free under Swift 6 strict concurrency with every generated type Sendable.
  • Phase 2: a state transaction touching 100 signals cannot be applied on the main thread inside 150 µs on a mid-range Android phone.
  • Phase 4: three engineers with no Rust background cannot go from zero to a running three-platform app in 15 minutes using only the docs.

§01Thesis: what makes teams trust a framework with their eyes closed

Blind trust is never given to a pitch. It is given to a tool that has been boring for long enough. Undra earns it with three product claims and five habits.

claim 1

State is the product

Calling a Rust function from Swift was solved years ago. What no one has shipped is Rust state that SwiftUI, Compose and React observe natively, with one FFI crossing per change instead of one per value. Undra's reactive core is the moat; bindings are table stakes.

claim 2

Idiomatic or nothing

Generated Swift must pass review by a Swift engineer who does not know Rust exists: typed throws, async, @Observable, Sendable. Same for Kotlin (sealed interfaces, suspend, Flow, Compose State) and TypeScript (discriminated unions, Promise, hooks). No RustBuffer in anyone's autocomplete.

claim 3

The dev loop is the feature

Change a Rust function and see it in the running iOS app in about a second without rebuilding the app. Time-travel any transaction in a devtools inspector on any platform. Test the whole core with cargo test and fake ports. This is what KMP cannot do and what makes engineers evangelize.

Five habits that build trust

  1. One contract suite, three platforms. Every feature ships with a behavioral test that runs on the iOS simulator, an Android emulator and a headless browser. If the platforms disagree, CI is red.
  2. Benchmarks are tests. The budgets in §14 are asserted in CI against the budgets in §14, and the numbers are published on the site every release (we do not benchmark other frameworks; the comparison posts say why).
  3. Compatibility is a promise. A core built with Undra 1.x loads against bindings from any Undra 1.x; a mismatch fails at startup with a message, never with undefined behavior.
  4. Error messages teach. Every macro error says what is wrong, why, and the fix, with a link. The compiler is the onboarding.
  5. We ship on it first. A real store app with auth, offline cart and sync is built on public Undra APIs only, and it ships to TestFlight, Play internal testing and the web on every release.

Say it out loud

Undra's adoption wall is hiring, not technology. Most mobile teams have zero Rust engineers. The product answer is that an Undra core reads like TypeScript with types that mean something: the macros hide lifetimes, the runtime hides threads, and the docs assume the reader has never opened a Rust book. The commercial answer is that the first customers are the companies already running Rust cores by hand (fintech, security, messaging, infrastructure-adjacent) who are paying three teams to maintain the glue.

§03Fifteen minutes from nothing to three running apps

The onboarding is measured with a stopwatch and real engineers, and the number is a release gate. Here is what those fifteen minutes look like.

$ cargo install undra-cli                     # or: brew install undra
$ undra init acme-core --targets ios,android,web
$ cd acme-core && undra dev                   # core runs on your laptop; apps connect over the wire
$ undra build --release                       # AcmeCore.xcframework + Swift package
                                             # acme-core.aar + Kotlin sources
                                             # @acme/core: ESM + .d.ts + .wasm
$ undra adopt ios ../AcmeApp.xcodeproj        # adds the package and a bootstrap; touches nothing else
$ undra doctor                                # toolchains, SDKs, signing, on one screen, with fixes

The core you write

One attribute, #[undra::api], marks anything that crosses the boundary. A few specialized attributes add semantics: #[undra::error], #[undra::store], #[undra::port]. There is no IDL file; the Rust source is the schema and rustc checks it.

use undra::prelude::*;

// Records become Swift structs, Kotlin data classes, TS interfaces.
#[undra::api] #[derive(Clone)]
pub struct Todo { pub id: Uuid, pub title: String, pub done: bool }

#[undra::api]
pub enum Filter { All, Active, Done }

// Typed errors: Swift typed throws, Kotlin sealed exceptions, TS error classes.
#[undra::error]
pub enum TodoError {
    #[error("title cannot be empty")] EmptyTitle,
    #[error(transparent)] Http(#[from] HttpError),
}

// A store: signals the UI observes, commands the UI calls.
#[undra::store]
pub struct Todos {
    ctx: Ctx,
    todos: Signal<Vec<Todo>>,
    filter: Signal<Filter>,
    visible: Computed<Vec<Todo>>,
}

#[undra::api]
impl Todos {
    pub fn new(ctx: Ctx) -> Self {
        let todos = Signal::new(vec![]);
        let filter = Signal::new(Filter::All);
        let visible = Computed::new((&todos, &filter), |(t, f)| {
            t.iter().filter(|x| f.matches(x)).cloned().collect()
        });
        Self { ctx, todos, filter, visible }
    }

    pub fn set_filter(&self, f: Filter) { self.filter.set(f) }

    pub async fn add(&self, title: String) -> Result<Todo, TodoError> {
        let title = title.trim().to_owned();
        if title.is_empty() { return Err(TodoError::EmptyTitle); }
        let todo = Todo { id: self.ctx.rng().uuid(), title, done: false };
        self.todos.update(|list| list.push(todo.clone()));          // transaction 1 → UI
        self.ctx.mutate(SaveTodo(todo.clone())).optimistic().await?; // transaction 2 on ack or rollback
        Ok(todo)
    }
}

What each platform engineer sees

Notice what is absent: no buffers, no handles, no callbacks, no "bridge" object. Reading visible is a plain property read in every language, because the value is mirrored on the platform side and never crosses the boundary on read.

import AcmeCore

struct TodoScreen: View {
    @State private var todos = Todos(ctx: .shared)   // generated @Observable final class
    @State private var draft = ""

    var body: some View {
        List(todos.visible) { Text($0.title) }        // property read, zero FFI calls
        TextField("New todo", text: $draft).onSubmit {
            Task { try await todos.add(title: draft) } // async throws(TodoError)
        }
    }
}
@Composable
fun TodoScreen(todos: Todos = rememberUndra { Todos(ctx = Undra.shared) }) {
    val visible by todos.visible                 // Compose State<List<Todo>>, zero FFI calls
    val scope = rememberCoroutineScope()
    var draft by remember { mutableStateOf("") }

    LazyColumn { items(visible, key = { it.id }) { Text(it.title) } }
    TextField(draft, onValueChange = { draft = it })
    Button(onClick = { scope.launch { todos.add(draft) } }) { Text("Add") }  // suspend, throws TodoError
}
import { Todos, TodoError } from "@acme/core";
import { useUndra, useSignal } from "@acme/core/react";

export function TodoScreen() {
  const todos = useUndra(Todos);               // core runs in a Worker; you never notice
  const visible = useSignal(todos.visible);   // useSyncExternalStore, no round trip

      <input value={draft} onChange={e => setDraft(e.target.value)} />
    </form>
  );
}

§04Migration ladder: every rung ships

Nobody rewrites a working app. Undra is adopted feature by feature, and each level is a state a company can stay in forever. The framework is designed so that the existing Swift, Kotlin and TypeScript code never has to know a migration is happening.

How coexistence works

At L1 and L2 the existing app keeps its own state management. The generated store class exposes signals that the old code can read like any other property, and the old code can push events into the core through ordinary commands. There is no "bridge" object to learn; a Kotlin ViewModel holding an Undra store next to its own StateFlows is unremarkable code. The undra adopt command adds the package dependency and a one-line bootstrap, and edits nothing else in the project.

The migration guides are written per source: "from KMP shared module", "from UniFFI", "from Crux", "from a TypeScript monorepo". Each is a checklist with a worked example and a codemod where one is possible (UniFFI's .udl maps mechanically onto #[undra::api], so that one is automated).

§05System shape: who writes what

The most useful architecture diagram answers one question for a new engineer: which parts do I write, which parts are generated, and which parts does the framework ship. Here it is.

Layer responsibilities

Native views

Own navigation, gestures, animation, accessibility, platform APIs with a UI surface (camera, share sheet, widgets). They read store signals as properties and call store commands. They hold only view-local state (text field drafts, scroll position).

Generated package

One class per store and object, one type per record and enum. Contains no logic, only the mapping between platform idioms and the wire. Regenerated on every core build; never edited by hand; checked into the app repo so builds are reproducible.

Platform runtime

The only code that knows about the FFI. Owns handle lifetimes, the async bridge, the state mirror, main-thread delivery, and the default adapters. Versioned in lockstep with the core's wire format.

Core

Pure Rust with no platform SDK linked in. Talks to the world only through ports, which makes it testable with cargo test and fake adapters, and runnable on a laptop for the remote dev loop.

Rules the macro enforces

  • Closed world. A type crosses only if it is in this table or is itself #[undra::api]. Generics are monomorphized per use; trait objects, lifetimes in public signatures, raw pointers and Box<dyn Fn> are rejected with a fix-it.
  • Newtypes stay typed. struct UserId(Uuid) becomes a distinct Swift struct, a Kotlin value class and a branded TypeScript type, so IDs do not get mixed up across the boundary either.
  • Keyed collections. #[undra(key = "id")] on a Vec<T> field of a store tells the mirror to send keyed patches (insert, remove, move, update) instead of the whole list, and gives SwiftUI, Compose and React stable identity for animations.
  • Lazy collections. Lazy<Vec<T>> crosses as a handle with paged access, so a 50,000-row table is never serialized. Virtualized lists on every platform pull pages through it.
  • Evolvable records. Fields can be added with #[undra(default)] and removed with #[undra(deprecated = "1.4")]; the schema hash covers layout, so mixing versions fails loudly at load instead of silently misreading bytes.

§07Reactive state: signals, transactions, one crossing per change

This is the part no incumbent has. Fine-grained signals in the core, a mirror of observed values on each platform, and a change-set protocol that turns any number of signal writes into a single crossing and a single render pass.

The model

  • Signal<T> holds a value. Computed<T> derives lazily from other signals with automatic dependency tracking, in the style of Solid and Leptos. Effect runs core-side reactions (persist on change, log, schedule a refetch) and never exists on the platform side.
  • Every write happens inside a transaction. A bare set or update is its own transaction; ctx.txn(|t| …) batches many. Transactions commit on the core loop in order, so the mirror always reflects a transaction-consistent snapshot and never half a change.
  • At commit, the runtime computes the dirty set (signals written, plus computeds that depend on them and are observed somewhere) and encodes a change-set: an ordered list of (signal id, value or keyed patch). One buffer, one crossing.
  • Each platform runtime holds a mirror: decoded current values for every observed signal. Reads on the platform are plain memory reads. The mirror is updated on the main thread in one hop, which SwiftUI, Compose and React each turn into exactly one render pass.
  • Observation is per store, batched: the runtime tells the core which signals have at least one observer, and the core stops encoding values nobody is looking at. Computeds that nobody observes are never evaluated.

Why this design and not the alternatives

Not callbacks per signal

A screen with forty bound values would cross the boundary forty times per change and re-render forty times. Change-sets are the difference between "works in a demo" and "works in the settings screen of a real app."

Not a whole view model

Re-emitting all state on every event is simple and it is what Crux does. It is also O(screen) per keystroke and makes stable list identity impossible. Keyed patches cost O(change) and keep animations correct.

Not synchronous reads across the boundary

If reads crossed, worker mode on the web and the remote core in development would both be impossible, because both make every crossing asynchronous. Local reads are what let one API work in-process, in a Worker, and over a socket.

Coalescing (ADR-031, in progress)

Today each transaction's change-set is applied in one main-thread hop. Once ADR-031 lands, change-sets committed before the platform's next frame are merged, so a burst of transactions from a network response becomes one render. Apps that need every intermediate state (progress bars) opt out per signal.

Time travel comes for free

Every transaction has an id, a parent and a change-set. Record them and you have a log that replays deterministically, because the core reads time and randomness only through ports (§15, rule 12). A snapshot is the encoded state of every signal. The devtools inspector (§13) scrubs through transactions on any platform, and crash recovery (§12) restores from the last snapshot plus the log. None of this needed extra design; it fell out of the transaction model.

§08Data layer: TanStack Query semantics, one implementation, three platforms

The most-loved library in web frontend exists because async server state is hard to get right. Undra ships those semantics in the core, so caching, staleness, retries, optimistic updates, persistence and the offline queue behave identically on every platform and are written once.

#[undra::query(key = "todos", stale = "30s", persist)]
async fn todos(ctx: &Ctx) -> Result<Vec<Todo>, HttpError> {
    ctx.http().get("/todos").json().await
}

#[undra::mutation(idempotent)]
async fn save_todo(ctx: &Ctx, todo: Todo) -> Result<Todo, HttpError> {
    ctx.http().post("/todos").json(&todo).send().await
}

// In a store command: optimistic patch, automatic rollback, targeted invalidation.
ctx.mutate(SaveTodo(todo.clone()))
   .optimistic(|cache| cache.todos().push(todo.clone()))
   .invalidates([Todos::KEY])
   .await?;

A query is exposed to the platforms as a small object of signals: data, status, error, fetching, updated_at. Because they are signals, the UI binds to them exactly as it binds to any store, and a refetch is just another change-set.

Included in v1

  • Cache keyed by structured keys with prefix invalidation; stale_time, gc_time, in-flight dedup, request cancellation when the last observer leaves.
  • Retry policy with jittered exponential backoff, per query or global; refetch on focus, reconnect and interval, driven by the Lifecycle and Connectivity ports.
  • Mutations with optimistic patches, rollback, invalidation, and an idempotent offline queue with ordering guarantees.
  • Infinite queries with cursor pages, exposed as a keyed Lazy list so virtualized UIs never hold the whole thing.
  • Persistence of the cache and queue via Kv with schema-hash versioning; hydration completes before the first render within a startup budget (§14).
  • Devtools view of the whole cache with staleness, observers and last fetch, on every platform.

Not in v1 and deliberately so: a full sync engine with conflict resolution. It belongs on this foundation and is the first item on the horizon (§20), but it is a product in its own right and would double the surface area of 1.0.

§09Ports and adapters: the core never links a platform SDK

The core declares what it needs as traits. Undra ships a default implementation of each on every platform, and an app can replace any of them in Swift, Kotlin or TypeScript by implementing the generated protocol. Tests replace them with fakes. This one rule is what makes the core runnable on a laptop, testable in milliseconds, and portable to a fourth platform later.

Design notes

  • Kv is Rust-owned on native. The default Kv adapter on iOS and Android is a bundled SQLite driven from Rust through the Fs port, so persistence semantics (transactions, migrations, corruption handling) are identical on both. Web uses IndexedDB because SQLite-in-wasm with OPFS is still too uneven across browsers to be a default; it is available as an opt-in adapter.
  • SecureStore is honest about the web. There is no Keychain equivalent in a browser. The web adapter uses WebCrypto with a non-extractable key in IndexedDB, and the docs say plainly what that protects against and what it does not.
  • Ports are async and cancellable by construction, so a port implementation never blocks the core loop, and a command that is cancelled cancels its port calls.
  • Port calls are observable. Every call is a span in the Telemetry port and a row in devtools, and can be recorded to a file and replayed in a test. A production bug reproduces on a laptop from its recording.

§10The boundary and the three runtimes

One wire format is the ABI. Swift, Kotlin and TypeScript codecs are generated from the schema, so the platform runtimes are thin, identical in behavior, and testable against each other with property-based round trips.

iOS

  • The core is a cdylib with a C ABI of a dozen exported functions (call, cancel, subscribe, release, restore) packaged as an XCFramework for device arm64 and simulator arm64/x86_64, inside a Swift Package with the generated sources. No Objective-C anywhere.
  • Stores are generated as @MainActor @Observable final class; records are value types that are Sendable, Hashable, Codable. The mirror lives on the main actor, which is also what makes the whole package compile clean under Swift 6 strict concurrency.
  • Async calls use withCheckedThrowingContinuation; the Rust future completes through a C callback carrying the continuation. Task cancellation calls undra_cancel(call_id), which drops the future.
  • Objects are generation-tagged handles into a slab, never raw pointers, so a stale handle is an error rather than a use-after-free. deinit releases; explicit close() is available for deterministic cleanup.

Android

  • JNI, with natives registered in JNI_OnLoad so there is no name lookup per call. Primitives cross as JNI primitives; change-sets arrive in a direct ByteBuffer that Kotlin decodes without a copy. Strings cross as UTF-8 bytes and are decoded in Kotlin, which is both faster than modified UTF-8 and correct for supplementary characters.
  • Stores expose Compose State<T> properties, with a StateFlow<T> view for non-Compose code. Mirror updates are posted to Dispatchers.Main.immediate.
  • Commands are suspend functions over suspendCancellableCoroutine; coroutine cancellation calls undra_cancel. Handles are AutoCloseable and registered with java.lang.ref.Cleaner as a backstop.
  • Built with NDK r27 or newer, 16 KB page-size aligned, ABIs arm64-v8a and x86_64 by default, armeabi-v7a opt-in. The AAR carries the .so files and the generated Kotlin.

Web

  • Target wasm32-unknown-unknown. wasm-bindgen is used only for the runtime's dozen edge functions; per-type glue is generated from the schema as TypeScript codecs, identical in shape to the Swift and Kotlin ones. Output is an ESM package with .d.ts, built with LTO and wasm-opt -Oz, loaded with streaming compilation.
  • The core runs in a Web Worker by default, so parsing a large response never janks the main thread. Worker mode is possible only because reads are local (§07); commands are already async, so nothing in the API changes.
  • Main-thread mode is one flag away for SSR, tests and small apps; there the codecs read Uint8Array views straight from wasm memory with no copy. Node, Bun and Deno are supported targets for server rendering and CI.
  • Framework bindings are thin: useUndra and useSignal for React (over useSyncExternalStore), a toRef adapter for Vue, the store contract for Svelte, passthrough for Solid.

§11Threading: one place mutates state

Every hard concurrency bug in a mobile app is two threads disagreeing about state. Undra removes the disagreement: exactly one thread owns signal state, and everyone else sends it messages.

  • Ordering guarantee: transactions commit in the order they complete on the core loop, and change-sets are delivered in commit order. A platform never observes state from transaction 8 before transaction 7.
  • Reentrancy: a command may call another store's command; a port adapter may not call back into the core synchronously. The runtime enforces the second rule with a debug assertion and a devtools warning.
  • Priorities: commands carry a priority (user-interactive, default, background). The core loop drains user-interactive first, which keeps a typing indicator responsive during a bulk sync.

§12Errors, panics and crash recovery

The host app must never die because the core did. A panic in Rust becomes a typed error on the platform, the state stays consistent, and on the web the core can restart itself from a snapshot faster than a user can notice.

Errors are values

Result<T, E> with #[undra::error] enums becomes typed throws in Swift, a sealed exception hierarchy in Kotlin, and error classes in TypeScript. No stringly-typed errors, ever. Error enums may carry data, and #[from] conversions keep the Rust ergonomic.

Panics are contained

On native the core builds with panic = "unwind" and every boundary entry is wrapped in catch_unwind. A panic becomes UndraPanic { message, backtrace }, delivered as an error to the caller and as an event to the Telemetry port. The app keeps running.

Transactions are atomic

Signal writes inside a transaction go to a copy-on-write overlay and are committed at the end. A panic mid-transaction discards the overlay, so a half-applied state is impossible even when code is wrong.

Web restarts from snapshot

wasm has no unwinding, so a panic traps. The runtime catches the RuntimeError, re-instantiates the module, restores the last snapshot and replays the transaction log since then, typically in well under 100 ms. The UI sees a recovering signal flip and nothing else.

Symbols and observability

undra build emits symbol files for every target: Rust frames appear in the iOS dSYM, Android gets stripped .so files plus symbol files ready for Play Console and Crashlytics upload, and the wasm build gets a source map. A Rust backtrace in a crash report reads like a Rust backtrace, with file and line. The Telemetry port emits spans for every command, transaction, query fetch and port call, and the default adapters forward them to OpenTelemetry-compatible exporters, so an app's existing tracing sees inside the core on day one.

§13The dev loop: the reason engineers will evangelize

Flutter's most persuasive feature has always been hot reload. Undra gets the same effect for the core without owning the UI, because the core can run anywhere the wire reaches.

DevTools

One inspector, connected to any platform, showing the transaction timeline with time-travel scrubbing, the signal dependency graph with which platform observes what, the query cache with staleness and observers, the port call log with timings, live handle counts, and a per-screen FFI crossing counter with the budget from §14 drawn on it. The crossing counter is the feature that turns performance from a belief into a number a junior engineer can watch.

Testing, in the shape of a pyramid

  • Core unit tests (most of them): plain cargo test with the shipped fakes. Advance the fake clock, script connectivity, assert on transactions. Milliseconds each.
  • Contract tests (generated): property-based round trips of every schema type through each language's codec, and behavioral tests of async, cancellation, streams and change-sets that run on the iOS simulator, an Android emulator and headless Chromium. This suite is the definition of "the platforms agree."
  • Record and replay: a port session recorded in production (with consent, through the Telemetry port) replays on a laptop with the same core build and reproduces the bug deterministically.
  • App integration tests (few): the platform's own UI test tooling against the real core, kept to smoke coverage because everything below the UI is already tested faster elsewhere.

§15Engineering constitution

This project will be built largely by AI coding agents working from this document. Agents drift unless the rules are explicit, checkable and few. These twelve are non-negotiable; each has a CI check or a review checklist item behind it.

  1. R1
    The schema is the only truth. A public type or function exists only if undra-meta can describe it. Every language's output is derived from that description; nothing is hand-written per platform except the runtimes.
  2. R2
    Unsafe lives in two crates. unsafe is permitted only in undra-ffi and undra-wire, every block carries a // SAFETY: comment, and both crates run under Miri and the sanitizers in CI. A PR that adds unsafe elsewhere is closed without review.
  3. R3
    Generated code must pass native review. A Swift, Kotlin or TypeScript engineer who has never seen Rust approves the generated package as code they would write. Golden-file snapshot tests lock the output; changing a snapshot requires a reviewer from that language.
  4. R4
    Every feature lands whole. Rust unit tests, contract tests on all three platforms, a benchmark if the boundary is touched, and a docs page. A feature missing any of these is not merged, however good the code.
  5. R5
    Reads never cross; writes cross once. No generated getter may call into the core. A transaction produces at most one change-set. A test counts crossings per scenario and fails on any increase.
  6. R6
    Nothing escapes as a panic or an abort. Every boundary entry is guarded; every error is a typed value; the host app is never terminated by the core.
  7. R7
    Compatibility is checked at load and at build. The schema hash is verified when the core loads; cargo semver-checks runs on every public crate; a breaking change to the wire is a major version and a written migration.
  8. R8
    Macro errors teach. Every rejection names the problem, the reason and the fix, with a stable error code and a docs link. A new error code is added with its docs page in the same PR.
  9. R9
    Budgets are tests. The §14 table lives in the repo as benchmarks; a regression past a budget fails CI. Numbers are published per release.
  10. R10
    We ship on it first. The reference store app uses only public APIs and is released to TestFlight, Play internal testing and the web on every tagged release. If dogfooding hurts, that pain is the next milestone.
  11. R11
    Boundary changes need an ADR. Anything that touches the wire, the runtime model, the threading model or the generated public shape is decided in a short written record before code, appended to §18.
  12. R12
    The core is deterministic. No wall-clock reads outside the Clock port, no randomness outside the Rng port, no ambient I/O. This is what makes replay, time travel and record-and-replay debugging correct rather than approximate.

§18Decision log

Short records of the decisions that shape everything else. Each says what was chosen, what was rejected, and why. New ones are appended, never edited.

ADR-001The Rust source is the IDL

Chosen: proc-macros emit schema metadata into the compiled artifact; undra-bindgen reads it. Rejected: a separate .udl or .idl file. Why: one source of truth that rustc type-checks, no drift, no second syntax to learn. UniFFI's proc-macro mode validates the approach.

ADR-002A binary wire format with generated codecs on every side

Chosen: dense little-endian format, versioned by a schema hash, codecs generated per type in Rust, Swift, Kotlin and TypeScript. Rejected: JSON (slow, lossy for integers and bytes), Protobuf and FlatBuffers (a second schema language and a dependency on every platform). Why: the format is small enough to own, fuzz and keep stable, and generating codecs from our own schema keeps every platform identical.

ADR-003Objects cross as generation-tagged handles

Chosen: Arc<T> in a slab; a u64 handle with a generation tag crosses; foreign finalizers release; explicit close() available. Rejected: raw pointers. Why: a stale or forged handle is an error, never memory corruption, and leaks are countable in devtools.

ADR-004One core loop owns all state

Chosen: a single thread commits transactions in order; I/O and CPU work run elsewhere and return values. Rejected: free-threaded signals with locks. Why: deterministic ordering, one change-set per transaction, and no lock a user can misuse. The cost, serialized commits, is invisible at app scale and measured by a budget.

ADR-005Change-sets, not per-signal callbacks, not whole view models

Chosen: the dirty set of observed signals is encoded once per transaction, with keyed patches for lists. Rejected: a callback per signal (O(signals) crossings), and re-sending all state (O(screen) per event, no stable identity). Why: §07; this is the moat.

ADR-006Reads are local; commands are async

Chosen: every platform holds a mirror of observed values; all boundary calls are asynchronous. Rejected: synchronous getters into the core. Why: it makes Worker mode and the remote core transparent, keeps the UI thread free, and is what makes "zero crossings on read" true.

ADR-007Ports are traits; the core links no platform SDK

Chosen: hexagonal architecture with shipped default adapters per platform and shipped fakes. Rejected: calling platform APIs from Rust via C bindings. Why: testability, the remote core, and the fourth platform.

ADR-008The web core runs in a Worker by default

Chosen: Worker mode default, main-thread mode by flag. Rejected: main-thread default. Why: wasm compute on the main thread is the most common way a wasm app feels worse than a JS one; ADR-006 makes the Worker free for app code.

ADR-009Remote core is a transport swap, not a separate mode

Chosen: the runtime's transport is pluggable; dev builds use WebSocket and route port calls back to the device. Rejected: dynamic library reloading on device (impossible on iOS devices, fragile elsewhere). Why: it costs nothing that ADR-002 and ADR-006 did not already pay for, and it works on real hardware.

ADR-010Panics are errors on native and a restart on the web

Chosen: catch_unwind at every native entry; trap, re-instantiate and restore from snapshot on wasm. Rejected: panic = "abort" on native. Why: the host app must never die for a bug in the core, and the transaction model makes restoration exact.

ADR-011Kv persistence is Rust-owned SQLite on native, IndexedDB on the web

Chosen: bundle SQLite for iOS and Android through the Fs port; IndexedDB default on the web with SQLite-in-wasm as an opt-in. Rejected: platform stores (Core Data, Room) behind an abstraction. Why: identical persistence semantics on both mobile platforms; the web opt-in stays open until OPFS support is uniform.

ADR-012UI stays native in 1.0

Chosen: no shared rendering. Rejected: a Rust UI toolkit or shared UI schema. Why: §00. This can be revisited in §20 only with evidence from shipped apps that the native-view layer is where teams still hurt.

§20Horizon: what comes after 1.0, and what still does not

Everything here is designed for, and none of it is built in 1.0. The order is by leverage: each item makes the previous ones more valuable.

horizon 1

Undra Sync

A local-first sync engine on top of Query: CRDT-backed documents, per-collection conflict policies, partial replication, end-to-end encryption through SecureStore. This is the product companies pay for, and every piece of 1.0 (transactions, keyed patches, offline queue, deterministic core) is a prerequisite for it.

horizon 2

Undra Cloud

Hosted sync, shared devtools sessions (a teammate opens the transaction log from your bug report), core telemetry and crash symbolication as a service. The framework stays open source; the services are the business.

horizon 3

Desktop and beyond

macOS already works through the Swift package. Windows and Linux arrive as a C# runtime and a GTK or Tauri-style shell; the wire and the port model are unchanged, which is the point of ADR-007. Any language with a C FFI can host an Undra core.

horizon 4

A port marketplace

Payments, analytics, auth providers and feature flags as ports with community adapters, so a Stripe or Auth0 integration is written once in Rust and lands on three platforms with native UI hooks.

What Undra still will not do

Render pixels. The question comes up every quarter and the answer is the same until shipped apps show that native views are where teams still lose time. If that evidence arrives, the honest experiment is a shared UI schema for content-heavy screens rendered by native components, never a shared renderer. Until then, a SwiftUI view that reads Rust state is the best possible iOS view, and that is the promise.

Closing

The industry has spent a decade proving that sharing UI across platforms is a compromise and sharing logic is a chore. Undra's bet is that the chore is the whole opportunity: make one correct core so pleasant to write, bind, debug and ship that nobody wants to write the same cache a third time. Build the boundary first, then the state, then the dev loop, and measure everything with a stopwatch.

Undra is a working name; check trademark and namespace availability before anything public. Timelines assume a small core team with AI agents doing most of the typing and a resident reviewer for each of Swift, Kotlin and TypeScript.
