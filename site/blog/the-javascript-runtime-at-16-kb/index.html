Fifteen levers: the JavaScript runtime at 16 KB

What a hello-world page loads up front of @undra/runtime went from 22,100 to 15,774 bytes gzipped, under a 16,000-byte budget. Nothing was removed: what left the first chunk loads with what needs it. Here are the fifteen levers, and the four defects the review caught.

Where the bytes were

The web size decision (ADR-052) asked for 16 KB of runtime up front. An earlier piece reached 21.2 KB and concluded that 16 KB would mean removing behaviour; five pieces then added 0.9 KB, and the gate stood at 22,100 bytes with no room. Instead we attributed every byte: a script charges each byte of the minified chunk, and each bit of its gzip stream, to its declaration. The largest shares:

Three things stood out. A hello page shipped code it cannot run: streams the template does not have, reconnection for a core that is not remote, 20 of 24 codecs. Where the bundler emits a module is decided by re-exports, not by use: a module reached through any file with code of its own lands in the first chunk. And the sentences of errors were about a tenth of the chunk.

Row 15 changes what is counted, not what is shipped, so the helper has a gate of its own: with it, the page loads 16,285 bytes against 16,600. Row 13 is the largest single lever. A production page carries an error's class, kind and fields, and its text is T<code> with a link to the error codes; the development build keeps the sentences.

What left, and what stays

What left loads when it is first needed: stream support, the framed transports' codecs, reconnection, the observe waiters, stats and background runs, the codecs a schema does not name. What stays up front stays for a reason we measured:

  • Keyed-patch merging, because read-your-writes drains are synchronous and could not wait for a chunk.
  • The mirror's compaction, because its backlog bound must hold offline too.
  • Object identity, because every app's first screen waits for it.
  • Connectivity and Lifecycle events, about 530 bytes: a hello core listens to neither, but nothing tells the page so. That needs the core to say when it starts listening, which is an ABI decision with its own record. It is the next lever.

What the review caught

The adversarial review reproduced every number to the byte and found four High defects at the levers' edges:

  • A stripped declaration. reclaim was marked internal, so the published types dropped it, and generated bindings that import it failed tsc against the installed package. Every suite aliased the sources and stayed green. A test now asks the compiler about every name the generator imports.
  • Lost order. snapshot() and restore() ran after an await import(), which yields even when the module is cached, so a call made after restore() reached the core first. They run at the call again.
  • A fetch at the wrong moment. The background drain at pagehide needed a chunk, at the one moment a page cannot fetch one. It calls the core directly now.
  • Codes where data was expected. The production build had turned a WebSocket close reason, which reaches the server, and port errors, which reach the core, into codes. Text that leaves the runtime as data is a sentence in both builds.

The fixes cost 131 bytes, to 15,811; smaller fixes and a later merge left the record at 15,774.

What it cost

An awaited call is 4% slower on Node, from 313 to 316 nanoseconds to 325 to 333; callSync did not move. The development build's first chunk is 21,151 bytes and is not gated, since a development page is served module by module. The page that uses every feature loads 39,922 bytes, less than the 42,385 it loaded before. All three numbers are gated in CI; a change that grows the chunk fails the build and names the lever left.

Every claim and its source: the claims ledger. The full record is ADR-057 and its review.
